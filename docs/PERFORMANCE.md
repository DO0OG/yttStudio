## SW vs GPU 백엔드 — SW 채택

GPU Render API의 readback 비용:

| 해상도 | GPU readback | SW 복사 |
|---|---:|---:|
| 1080p60 | 1.553 ms | 0.488 ms |
| 1440p60 | 3.853 ms | 1.077 ms |
| 2160p30 | 4.392 ms | 2.291 ms |

**결정: `MPV_RENDER_API_TYPE_SW`를 기본 경로로 채택.**

근거:
- 세 목표 해상도 모두 SW로 실시간 재생을 달성했다
- **SW 복사 비용이 GPU readback보다 모든 해상도에서 낮다**
- GPU는 CPU 사용량이 낮지만 readback·메모리·크로스플랫폼 GL context 관리 비용이 더 크다
- airspace 제약 때문에 어차피 픽셀을 CPU로 가져와 `WriteableBitmap`에 blit해야 한다.
  GPU 경로의 이점이 readback에서 상쇄된다

> 초기 설계는 SW 렌더러를 "fallback/debug 전용"으로 보고 GPU 우선 검토를 권고했으나,
> **M2 benchmark 결과로 SW를 기본으로 확정**했다. 원래 설계도
> "M2 benchmark 후 결정한다"고 명시하고 있으므로 절차 위반이 아니다.
> 이 결정을 근거와 함께 여기에 기록한다.

## 재생 · 스크럽 부하 (2026-08-28 실측)

**측정 환경:** Windows 11, .NET 10 Release 빌드, 1080p 영상, `hwdec=auto-copy`
**방법:** 앱 안에 렌더 경로 계측을 넣어 탐색 · 렌더 · 건너뜀 횟수와 mpv 렌더 · 알파 채우기
시간, 전송 바이트를 누적하고 2초 구간의 차이를 읽었다. CPU · GPU 는 작업 관리자로 읽었다.

### 재생 중 프리뷰 렌더

프리뷰가 프레임마다 비트맵을 새로 만들고 PNG 품질 100 으로 압축했다가 곧바로 디코딩하고
있었다. 표시용 화소를 얻는 데 무손실 압축을 한 번 돌린 셈이다. 레이아웃도 렌더와 측정에서
두 번 계산했다.

| 1280×720 · 120 프레임 | 총 시간 | 프레임당 | 관리 힙 |
|---|---:|---:|---:|
| 변경 전 | 4,267.7 ms | 35.6 ms | 4.9 MB |
| 변경 후 | 14.4 ms | **0.12 ms** | 1.3 MB |

프레임당 35.6ms 는 30fps 예산 33ms 를 자막 렌더링만으로 넘긴 값이다. `WriteableBitmap` 을
재사용해 Skia 가 그 화소 버퍼에 직접 그리게 하고 레이아웃을 한 번만 계산한다. 관리 힙
수치는 과소평가다. `SKBitmap` 의 화소 버퍼는 비관리 메모리라 잡히지 않는다.

### 스크럽 탐색 간격

타임라인이나 슬라이더로 위치를 마구 옮길 때 GPU 가 팔십 퍼센트를 넘었다. 계측을 붙여 보니
탐색이 초당 아흔 번 가까이 나가고 있었다. 최소 간격을 두었다고 적어 두었으나 그 제한이
한 번도 걸리지 않고 있었다 — 간격의 기준을 진행 중인 탐색이 있는지로 삼은 탓이다.
`SeekAsync` 는 명령만 던지고 즉시 반환하므로 그 조건은 사실상 항상 거짓이었다.

기준을 직전에 실제로 내보낸 시각으로 바꾸었다.

| 같은 방식으로 끌었을 때 | 탐색 | 렌더 | 전송 | CPU | GPU |
|---|---:|---:|---:|---:|---:|
| 변경 전 | 66~98/s | 45~61/s | 360~490 MB/s | 10~15% | 80% 이상 |
| 변경 후 | 11~14/s | 12~14/s | 93~114 MB/s | 최대 10% | **최대 20%** |

mpv 렌더와 알파 채우기는 합쳐도 십 퍼센트대였다. CPU 병목이 아니라 탐색마다 디코더를
비웠다 다시 채우는 것이 원인이었다.

재생 경로는 건드리지 않았다. 재생 구간의 탐색은 0 이다.

> **로그를 읽을 때 주의.** 재생 중 mpv 렌더 시간이 구간의 99% 로 찍히는데 계산이 아니라
> 대기다. 같은 해상도인데 스크럽 때는 프레임당 1.4ms, 재생 때는 41ms 다. mpv 가 다음 프레임
> 표시 시각까지 그 호출 안에서 기다리기 때문이다.

### 되돌린 시도

프리뷰 렌더를 UI 프레임당 한 번으로 묶고 입력이 같으면 건너뛰는 방식, 그리고 큐 활성 구간
안에서 레이아웃과 히트박스를 재사용하는 방식을 넣었다가 되돌렸다. 실제 앱에서 재보니 CPU 와
메모리를 이전보다 더 먹었고 GPU 는 그대로였다.

재생 중에는 프레임 인덱스가 매 프레임 바뀌어 건너뛰기 판정이 성립할 수 없는데, 판정에 드는
비용만 프레임마다 더한 것이 원인이다. 프리뷰 렌더는 이미 프레임당 0.12ms 라 더 깎을 실익이
없다.

## 미측정 / 한계

- **실사 영상 미측정.** 생성 패턴 영상만 사용했다. H.264/HEVC 실사 콘텐츠는 디코드 부하가 다르다
- **Linux / macOS 미측정.** Windows에서만 쟀다
- 저사양 GPU / 통합 그래픽 환경 미측정
- 장시간 재생 시 메모리 증가 추이 미측정
- **GPU 수치는 작업 관리자 판독값이다.** 디코드 · 복사 · 3D 엔진별 분해는 하지 않았다
- 스크럽 최소 간격 70ms 는 눈으로 이어져 보이는 선에서 고른 값이다. 화면 주사율이나 영상
  키프레임 간격에 따른 최적값은 재지 않았다
